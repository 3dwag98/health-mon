Design documentation

Worker Health SDK

A message-driven worker can be alive and completely unable to consume. Process status does not say whether work is happening. This is how the SDK answers that question from the worker’s own connections — and what it asks of the code it is added to.

01The integration surface

The SDK is a library that runs inside the worker process. It is not a sidecar, an agent, or a service to deploy. Adding it to an existing worker means three edits — and, deliberately, no edits at all to the code that does the work.

Everything else is configuration. Which dependencies are checked, how often, which are critical, what counts as a stalled queue — all of it lives in worker-health.yaml, Django settings, or environment variables, and none of it is code.

Why instrument the client rather than the call site. The alternative is a context manager at each call — with tracker.dependency("postgres"): — which works, and which nobody finishes applying. A repository three constructors deep either receives a tracker it should not know about, or its queries are invisible. Wrapping the client once means the coverage does not depend on discipline.

02Covering a plain Python function

“One unit of work” is whatever the worker calls once per message. @handler dispatches on what the target actually is, because real consumers are not all plain functions:

# a function, sync or async
@health.handler(queue="billing.in")
def handle(msg): ...

# a generator — one message in, many values out, still one unit of work.
# Timed across the whole iteration; send/throw/close keep working.
@health.handler()
def split(msg):
    yield from rows(msg)

# a class-based consumer: __call__ is wrapped in place, so isinstance
# checks and anything holding the class keep working
@health.handler(queue="billing.in")
class BillingConsumer:
    async def __call__(self, msg): ...

# …or when the entry point has a name
@health.tracker.consumer_class(method="handle")
class BillingConsumer:
    def handle(self, msg): ...

The callable-instance case is the one worth naming. inspect.iscoroutinefunction(instance) returns False even when __call__ is async def, because the coroutine function is on the type. A decorator that inspects the instance therefore picks the synchronous wrapper and times how long it took to create the coroutine — every message reports as taking microseconds, and the processing check goes quietly blind. Dispatch is on type(obj).__call__.

Work that is not a message at all

A cron-like function, a polling loop, or a third-party client the SDK has no adapter for:

# A check of your own. Returns bool, Status, or CheckResult;
# if it raises, it reports `unknown` and no other check is affected.
@health.monitor.check("vendor-api", critical=False, interval=30, timeout=2)
def check_vendor():
    return vendor.status() == "ok"

# A dependency call the instrumentation cannot see. One context
# manager is still cheaper than writing an adapter.
with health.tracker.dependency("vendor-api"):
    vendor.charge(...)

# Attributing latency inside a multi-dependency handler.
with health.tracker.stage("billing.in", "postgres_txn"):
    ...

03Django workers that run via manage.py

A long-running Django worker is a management command that a supervisor keeps alive: python manage.py consume_billing. That shape has one problem that dominates every other design question here.

AppConfig.ready() is the only hook Django offers that runs after the app registry is populated and before a command executes — which makes it the right place to instrument the ORM, and a terrible place to start an HTTP server. It fires for every entry point: migrate, shell, collectstatic, a pytest run, the autoreloader's parent process, and every custom command a project has ever added. Settings-driven wiring has to guess from sys.argv which of them is a worker, and that guess decides which process binds a port.

What the base class provides

from worker_health_django import WorkerHealthCommand

class Command(WorkerHealthCommand):
    health_service = "billing-worker"
    health_queue = "billing.in"

    def handle(self, *args, **options):
        @self.tracker.handler(queue="billing.in")
        def handle_message(body):
            process_payment(body)      # ORM + cache observed automatically

        for raw in consume(stop=self.stopping):
            handle_message(json.loads(raw))

    def on_shutdown(self, signum):
        # one non-blocking thing; self.stopping is already set
        self.channel.connection.add_callback_threadsafe(self.channel.stop_consuming)

handle() is the method you would have written anyway. What changes:

WhatWhy it has to come from the base class
self.trackerDjango constructs the command, so nothing can be passed in. Without this, the alternative is reaching through a module-level global.
self.stoppingA threading.Event, set on the first stop signal. self.sleep(n) returns early on it; self.should_stop reads it. A consume loop that cannot be interrupted turns every deploy into a SIGKILL.

Ports, when there is more than one worker

Two manage.py workers on one host cannot both have 8080. In precedence order:

--health-port 8091                     explicit; wins over everything
health_port = 8091                     on the command class
"PORTS": {"consume_billing": 8091}     per command, by command name
"PORT": 8080  + instance ordinal       PM2 cluster: 8080, 8081, 8082…

The ordinal comes from NODE_APP_INSTANCE / PM2_INSTANCE_ID / pm_id, so instances: 4 lays a cluster out contiguously — and gives each copy a metric label that survives a restart, which a pid does not. If the chosen port is taken anyway the next twenty are tried, and the one actually bound is printed at startup and published to the host's run registry. A busy health port never stops a worker from starting.

Finding the workers on a host

manage.py worker_health is a new process. The monitor lives in the worker that is still running somewhere else, so reading it out of module state returns nothing — always, for the exact use the command exists for. Every worker that binds a port writes service, instance, pid and port to a per-user run directory; records whose process is gone are pruned by the next reader, so a SIGKILL leaves nothing behind.

$ python manage.py worker_health
billing-worker (http://127.0.0.1:8091, pid 4412): readiness=ready liveness=alive
  postgres           ok        observed      critical
  redis-cache        ok        observed      non-critical
  rabbitmq           ok        introspected  critical
  queue billing.in   received=8134 succeeded=8130 failed=4 depth=12

The standalone worker-health CLI reads the same registry, so worker-health --list works with no Django and no arguments.

04Three threads, two shared stores

The mechanism that makes the rest possible: nothing on the request path performs I/O. An endpoint reads a value that was already computed. That is what lets /live answer in microseconds while the worker is blocked inside a four-second handler, and what stops a supervisor polling every two seconds from becoming a load source on a database that is already struggling.

05The evidence ladder

A probe-first design reports healthy while a worker sits on a dead pooled connection: the probe opens its own socket, succeeds, and says nothing about the one the worker is actually blocked on. So a check prefers what the worker's own connection already proves, and falls back to asking only when the worker has gone quiet — and every result says which of the three it was, so a probe-backed green never reads like a traffic-backed green.

06Per-check state

A raw sample is not a status. One lost packet is not an outage, and a dependency that has just failed should not be asked again every two seconds while it is trying to recover. Each check runs its own small state machine over its samples, and the endpoints report the effective status — thresholds and TTL applied — never the last raw one.

Cold start. Once boot grace is over, a critical check that has never completed an evaluation — or whose last result has aged past its TTL — makes the worker unready, not degraded. “We have never managed to ask” and “we asked and it was fine” are not the same answer, and only one of them is a reason to route work here.

07Live, ready, and draining

Two endpoints, two different questions, two different consequences. Conflating them is the single most expensive mistake available here: a liveness probe wired to a dependency check restarts an entire fleet when a shared database goes down, and none of the restarts fix the database.

08Where the signals go

One snapshot, four audiences. Each gets the shape it can act on, and none of them causes any I/O to a dependency.

10Decisions, and what they cost

What is deliberately not here

  • No agent or sidecar. The evidence this design depends on — the worker's own pool, its own connection, its own traffic — only exists inside the process. A sidecar can only probe, which is the rung this design treats as the fallback.
  • No Celery integration. Recorded rather than built: celery inspect ping is answered from the main loop and documented not to respond while the worker is busy with a long task, so it reports unhealthy precisely when the worker is healthiest. That is the same failure this SDK is built to avoid, and the reason the answer is a separate thread with a cached snapshot.
  • No authentication on the health port. It binds where it is told and carries no secrets; loopback plus a supervisor is the deployment it is designed for.
